# KAPA Bank — Relational Model & Schema Specification

This document provides the formal **Relational Model**, table schemas, integrity constraints, and **ER &rarr; Relational Mapping Rules** for the **KAPA Bank Transaction Management System**.

---

## 1. Formal Relational Model (Text Representation)

```text
CUSTOMERS (
    customer_id (PK),
    name,
    email (UK),
    phone (UK),
    address
)

USERS (
    user_id (PK),
    email (UK),
    password_hash,
    display_password,
    role,
    customer_id (FK -> CUSTOMERS.customer_id),
    is_active,
    last_login,
    created_at
)

BANK_ACCOUNTS (
    account_id (PK),
    customer_id (FK -> CUSTOMERS.customer_id),
    account_number (UK),
    account_type,
    balance,
    status,
    created_date
)

BANK_TRANSACTIONS (
    transaction_id (PK),
    account_id (FK -> BANK_ACCOUNTS.account_id),
    transaction_type,
    amount,
    transaction_date,
    status
)

BANK_TRANSFERS (
    transfer_id (PK),
    from_account (FK -> BANK_ACCOUNTS.account_id),
    to_account (FK -> BANK_ACCOUNTS.account_id),
    amount,
    transfer_date,
    status
)

AUDIT_LOG (
    audit_id (PK),
    user_id (FK -> USERS.user_id),
    action,
    entity_type,
    entity_id,
    details,
    ip_address,
    created_at
)
```

## 3. ER Model to Relational Model Mapping Rules

Academic conversion from the conceptual ER Model to the logical Relational Model follows standardized database design steps:

### Step 1: Mapping Strong Entities
- **Rule:** For each strong entity type $E$ in the ER schema, create a relation $R$ that includes all simple attributes of $E$. Choose one key attribute as the Primary Key ($PK$).
- **Application:**
  - **Entity `CUSTOMER`:** Created relation `CUSTOMERS(customer_id PK, name, email UK, phone UK, address)`.
  - **Entity `BANK_ACCOUNT`:** Created relation `BANK_ACCOUNTS(account_id PK, account_number UK, account_type, balance, status, created_date)`.
  - **Entity `USER`:** Created relation `USERS(user_id PK, email UK, password_hash, role, is_active, last_login, created_at, display_password)`.

### Step 2: Mapping 1:1 Binary Relationships
- **Rule:** For a binary 1:1 relationship between $S$ and $T$, choose one relation (preferably total participation) and include the primary key of the other relation as a Foreign Key ($FK$). Include any relationship attributes.
- **Application:**
  - **Relationship `USER AUTHENTICATES AS CUSTOMER` (1 : 0..1):** A customer has at most one user account. Admin users do not correspond to customer accounts. Therefore, `customer_id` is placed as a nullable Foreign Key in `USERS` (`USERS.customer_id -> CUSTOMERS.customer_id`).

### Step 3: Mapping 1:M Binary Relationships
- **Rule:** For a binary 1:N relationship type, identify the relation $T$ on the "N-side" (many side) and include the primary key of the relation $S$ on the "1-side" as a Foreign Key ($FK$) in $T$.
- **Application:**
  - **Relationship `CUSTOMER OWNS BANK_ACCOUNT` (1 : M):** `customer_id` is included as Foreign Key in `BANK_ACCOUNTS`.
  - **Relationship `BANK_ACCOUNT HAS BANK_TRANSACTION` (1 : M):** `account_id` is included as Foreign Key in `BANK_TRANSACTIONS`.
  - **Relationship `USER TRIGGERS AUDIT_LOG` (1 : M):** `user_id` is included as Foreign Key in `AUDIT_LOG`.

### Step 4: Mapping Associative / Multi-Role Transfer Relationships
- **Rule:** When an entity participates in a relationship with multiple distinct roles (e.g. sender and recipient in a fund transfer), create an associative relation $R$. Include the primary keys of the participating entities as foreign keys with distinct role attribute names.
- **Application:**
  - **Relationship `TRANSFER (from_account, to_account)`:** Created relation `BANK_TRANSFERS` with two foreign keys referencing `BANK_ACCOUNTS(account_id)`:
    - `from_account` (Role: Source/Sender)
    - `to_account` (Role: Destination/Receiver)
    - `amount`, `transfer_date`, `status` (Relationship attributes)
    - `transfer_id` (Surrogate Primary Key)

## 4. Normalization Analysis (1NF, 2NF, 3NF, BCNF)

### First Normal Form (1NF)
- **Requirement:** Every attribute contains only atomic (indivisible) values, and there are no repeating groups.
- **Verification:**
  - All attributes across all 6 tables store atomic values (e.g. `email`, `amount`, `balance`, `status`).
  - No comma-separated lists or multi-valued arrays are stored in any column.
  - **Result: All relations strictly satisfy 1NF.**

### Second Normal Form (2NF)
- **Requirement:** Relation must be in 1NF, and no non-prime attribute is partially dependent on any candidate key (no partial functional dependency).
- **Verification:**
  - In all 6 tables, primary keys are single-attribute surrogate keys (`customer_id`, `account_id`, `transaction_id`, `transfer_id`, `user_id`, `audit_id`).
  - Partial dependencies can only occur when a candidate key is composite (consists of 2 or more attributes).
  - Since all candidate keys are single attributes, partial dependencies are mathematically impossible.
  - **Result: All relations strictly satisfy 2NF.**

### Third Normal Form (3NF)
- **Requirement:** Relation must be in 2NF, and no non-prime attribute is transitively dependent on the primary key (no $X \rightarrow Y \rightarrow Z$ where $Z$ is non-prime and $Y$ is not a superkey).
- **Verification:**
  - **`CUSTOMERS`:** Candidate keys are `customer_id`, `email`, `phone`. Non-prime attribute is `name`, `address`. Dependencies: `customer_id -> name, address`. No non-prime attribute determines another non-prime attribute.
  - **`BANK_ACCOUNTS`:** Candidate keys are `account_id`, `account_number`. Non-prime attributes are `account_type`, `balance`, `status`, `created_date`. All are determined directly by `account_id` or `account_number`. No non-prime transitive dependencies exist.
  - **`BANK_TRANSACTIONS`:** `transaction_id -> account_id, transaction_type, amount, transaction_date, status`. No non-prime determines another non-prime attribute.
  - **`BANK_TRANSFERS`:** `transfer_id -> from_account, to_account, amount, transfer_date, status`. All non-prime attributes depend directly on `transfer_id`.
  - **`USERS`:** Candidate keys are `user_id`, `email`. Non-prime attributes depend directly on candidate keys.
  - **Result: All relations strictly satisfy 3NF.**
