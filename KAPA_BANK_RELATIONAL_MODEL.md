# KAPA Bank — Relational Model & Schema Specification

This document provides the formal **Relational Model**, complete schema specifications, physical constraints, and **ER &rarr; Relational Mapping Rules** for the **KAPA Bank Transaction Management System**.

---

## 1. Formal Relational Model (Textual Representation)

```text
CUSTOMERS (
    customer_id (PK),
    name,
    email (UK),
    phone (UK),
    address
)

USERS (
    user_id (PK),
    email (UK),
    password_hash,
    display_password,
    role,
    customer_id (FK -> CUSTOMERS.customer_id ON DELETE CASCADE),
    is_active,
    last_login,
    created_at
)

BANK_ACCOUNTS (
    account_id (PK),
    customer_id (FK -> CUSTOMERS.customer_id),
    account_number (UK),
    account_type,
    balance,
    status,
    created_date
)

BANK_TRANSACTIONS (
    transaction_id (PK),
    account_id (FK -> BANK_ACCOUNTS.account_id),
    transaction_type,
    amount,
    transaction_date,
    status
)

BANK_TRANSFERS (
    transfer_id (PK),
    from_account (FK -> BANK_ACCOUNTS.account_id),
    to_account (FK -> BANK_ACCOUNTS.account_id),
    amount,
    transfer_date,
    status
)

AUDIT_LOG (
    audit_id (PK),
    user_id (FK -> USERS.user_id ON DELETE SET NULL),
    action,
    entity_type,
    entity_id,
    details,
    ip_address,
    created_at
)
```

## 3. Formal ER &rarr; Relational Mapping Rules & Steps

The conversion of the conceptual ER model to the relational schema follows the standard 7-step mapping algorithm:

### Step 1: Mapping Strong Entity Types
For each regular entity type $E$ in the ER diagram, create a relation $R$ that includes all simple attributes of $E$. Choose one key attribute as the Primary Key.
- `CUSTOMER` &rarr; `CUSTOMERS(customer_id PK, name, email UK, phone UK, address)`
- `USER` &rarr; `USERS(user_id PK, email UK, password_hash, display_password, role, is_active, last_login, created_at)`
- `BANK_ACCOUNT` &rarr; `BANK_ACCOUNTS(account_id PK, account_number UK, account_type, balance, status, created_date)`

### Step 2: Mapping 1:1 Relationship Types
For each binary 1:1 relationship type $R$ between $S$ and $T$, choose one relation (say $S$) and include the primary key of $T$ as a foreign key in $S$.
- **`USER authenticates as CUSTOMER` (1:1 optional):**
  - Place `customer_id` as a foreign key in `USERS`.
  - Since system administrators do not hold personal customer accounts, `USERS.customer_id` is defined as `NULLABLE`.

### Step 3: Mapping 1:M Binary Relationship Types
For each regular binary 1:M relationship type $R$, identify the relation $S$ that represents the participating entity type at the **"N" (many) side** of the relationship. Include the primary key of the relation $T$ representing the entity type at the **"1" side** as a foreign key in $S$.
- **`CUSTOMER owns BANK_ACCOUNT` (1:M):**
  - "1" side: `CUSTOMERS` (PK: `customer_id`)
  - "M" side: `BANK_ACCOUNTS`
  - Result: Add `customer_id` as foreign key into `BANK_ACCOUNTS`.
- **`BANK_ACCOUNT has BANK_TRANSACTION` (1:M):**
  - "1" side: `BANK_ACCOUNTS` (PK: `account_id`)
  - "M" side: `BANK_TRANSACTIONS`
  - Result: Add `account_id` as foreign key into `BANK_TRANSACTIONS`.
- **`USER triggers AUDIT_LOG` (1:M):**
  - "1" side: `USERS` (PK: `user_id`)
  - "M" side: `AUDIT_LOG`
  - Result: Add `user_id` as foreign key into `AUDIT_LOG`.

### Step 4: Mapping Recursive / Associative Relationship Types
When an associative relationship links two instances of the same entity set with relationship attributes, create a new relation $R$ representing the relationship. Include the primary key of the participating entity set as two distinct foreign key attributes with distinct role names.
- **`BANK_TRANSFER` (Inter-Account Transfer):**
  - Participating entity: `BANK_ACCOUNT` (PK: `account_id`)
  - Role 1: Source Account &rarr; `from_account` (FK &rarr; `BANK_ACCOUNTS.account_id`)
  - Role 2: Destination Account &rarr; `to_account` (FK &rarr; `BANK_ACCOUNTS.account_id`)
  - Relationship attributes: `amount`, `transfer_date`, `status`
  - Result: Create `BANK_TRANSFERS` with surrogate PK `transfer_id`.

## 4. Normalization Analysis (1NF, 2NF, 3NF, BCNF)

### 4.1 First Normal Form (1NF)
- **Criterion:** All attribute values are atomic; no repeating groups, sets, or nested records.
- **Proof:** Every column in every relation stores an atomic scalar value (`NUMBER`, `VARCHAR2`, `TIMESTAMP`). No column stores multi-valued CSV strings or arrays.
- **Result:** **1NF Satisfied**.

### 4.2 Second Normal Form (2NF)
- **Criterion:** Relation must be in 1NF and contain no partial functional dependencies (no non-prime attribute may depend on a proper subset of a composite candidate key).
- **Proof:**
  - `CUSTOMERS` Candidate Keys: `{customer_id}`, `{email}`, `{phone}` (all single-attribute).
  - `USERS` Candidate Keys: `{user_id}`, `{email}` (all single-attribute).
  - `BANK_ACCOUNTS` Candidate Keys: `{account_id}`, `{account_number}` (all single-attribute).
  - `BANK_TRANSACTIONS` Candidate Key: `{transaction_id}` (single-attribute).
  - `BANK_TRANSFERS` Candidate Key: `{transfer_id}` (single-attribute).
  - `AUDIT_LOG` Candidate Key: `{audit_id}` (single-attribute).
  - Since **no composite candidate keys exist in any relation**, partial functional dependencies are mathematically impossible.
- **Result:** **2NF Satisfied**.

### 4.3 Third Normal Form (3NF)
- **Criterion:** Relation must be in 2NF and contain no transitive functional dependencies ($X \rightarrow Y \rightarrow Z$ where $Z$ is non-prime and $Y$ is not a superkey).
- **Proof:**
  - In `CUSTOMERS`, all non-prime attributes (`name`, `address`) depend directly on the candidate keys (`customer_id`, `email`, `phone`).
  - In `BANK_ACCOUNTS`, `customer_id` is a foreign key. The account table does not store redundant customer attributes (`customer_name`, `customer_email`).
  - In `USERS`, `customer_id` references `CUSTOMERS` without duplicating customer details.
  - In all functional dependencies $X \rightarrow Y$, the determinant $X$ is a superkey.
- **Result:** **3NF Satisfied**.

### 4.4 Boyce-Codd Normal Form (BCNF)
- **Criterion:** For every non-trivial functional dependency $X \rightarrow Y$, $X$ must be a **superkey**.
- **Proof:**
  - For every functional dependency in the system:
    - $\text{customer\_id} \rightarrow \text{attributes}$ (Superkey)
    - $\text{email} \rightarrow \text{attributes}$ (Superkey)
    - $\text{phone} \rightarrow \text{attributes}$ (Superkey)
    - $\text{account\_id} \rightarrow \text{attributes}$ (Superkey)
    - $\text{account\_number} \rightarrow \text{attributes}$ (Superkey)
    - $\text{transaction\_id} \rightarrow \text{attributes}$ (Superkey)
    - $\text{transfer\_id} \rightarrow \text{attributes}$ (Superkey)
    - $\text{user\_id} \rightarrow \text{attributes}$ (Superkey)
  - Every determinant is a candidate key / superkey.
- **Result:** **BCNF Satisfied**.

## 5. Relational Constraints & Invariants Summary

1. **Entity Integrity:** All primary keys (`customer_id`, `user_id`, `account_id`, `transaction_id`, `transfer_id`, `audit_id`) are constrained by `NOT NULL` and generated by Oracle's internal identity engine.
2. **Referential Integrity:**
   - `BANK_ACCOUNTS.customer_id` &rarr; `CUSTOMERS.customer_id`
   - `USERS.customer_id` &rarr; `CUSTOMERS.customer_id` (`ON DELETE CASCADE`)
   - `BANK_TRANSACTIONS.account_id` &rarr; `BANK_ACCOUNTS.account_id`
   - `BANK_TRANSFERS.from_account` &rarr; `BANK_ACCOUNTS.account_id`
   - `BANK_TRANSFERS.to_account` &rarr; `BANK_ACCOUNTS.account_id`
   - `AUDIT_LOG.user_id` &rarr; `USERS.user_id` (`ON DELETE SET NULL`)
3. **Domain & Business Check Constraints:**
   - `balance >= 0`: Guarantees that accounts cannot be driven into negative balances.
   - `amount > 0`: Prohibits zero or negative transactions.
   - `from_account <> to_account`: Prohibits self-transfers.
   - `account_type IN ('SAVINGS', 'CURRENT')`
   - `status IN ('ACTIVE', 'BLOCKED', 'CLOSED')`
   - `role IN ('CUSTOMER', 'ADMIN')`
   - `is_active IN (0, 1)`
